# 18 · The HQ screen

Until now HQ was an API: every HQ job (adding a branch, reading the chain's day, taking a backup, making a staff account) meant a hand-made request. The HQ screen is a small web app that does those jobs in a browser. It answers question #33 in `docs/QUESTIONS.md` (option A: a screen the owner looks at each morning). It sends nothing; it only shows.

**Built (2026-11-28):** sign in, **Overview**, **Branches**, **Backups**, **Staff** (version 1) and **People**, **Attendance**, **Payroll**, **Pay setup** and **My pay** for employee accounts (HR and payroll pages). **Also built:** **Schedule** (shifts, rosters, leave, holidays and the plan beside what happened), **Purchasing** (purchase orders and what HQ owes suppliers) and **Stock suggestions**. **Not built yet:** the catalog; customers' balances; reports beyond today's totals; Arabic. Each of those is an API today (`docs/06`) and gets a page when it is needed.

## 1. Where it lives and how it is served

- Source: `cloud-hq/web` (Vite, React, TypeScript; its own folder inside the HQ project, like `till/web`). Build: `npm run build --prefix cloud-hq` writes `cloud-hq/web/dist`.
- **HQ serves it itself**, from `cloud-hq/web/dist` when that folder exists (or from `WEB_DIST`). Without a build HQ answers the API only. There is nothing else to install: the same address, `https://<HQ's name>/`, is the screen, and the screen talks to `/api/v1` on that same address.
- Development: `npm run dev --prefix cloud-hq/web` serves the screen on port 5174 and forwards `/api` to HQ on 4000.
- **Headers** (`cloud-hq/src/app.ts`): the screen's own files may load scripts and styles from HQ and nowhere else (`script-src 'self'`, no inline script, no eval, no foreign origin: the same policy as the till). The API keeps `default-src 'none'`, `no-store` and no framing. A route that sets its own headers (the payslip page needs an inline style) is no longer overridden: this was a real bug found while building the screen, since the page would have lost its style in a browser. A page address such as `/branches` belongs to the app's router, so a browser asking for it gets the app; the API keeps its JSON 404s. HQ's `Host` and `Origin` checks apply to the screen too.

## 2. The pages

| Page | Who | What |
|---|---|---|
| **Sign in** | everyone | Name and password (`POST /auth/login`). A wrong answer says "the name or the password is wrong". A new account is stopped at **Choose your own password** until it has one (at least 12 characters). An `employee` account sees a short note: their payslips are not on this screen yet. |
| **Overview** | any staff | "Everything is fine" or "Something needs a look" with each problem in plain words (from `GET /monitoring/branches`, docs/17 §5); today's sales, net sales, returns and profit for the chain; a row for every branch with its state, when it was last heard, today's sales and open tills; the backup in one line. Refreshes each minute. Figures are what the branches have sent so far today (Beirut time). |
| **Branches** | any staff read; admin changes | The branches and their state; **add a branch** (code, name, shop or stock) and the **one-time code** is shown once, in a box, to type at the branch; **New code** for a branch that has not connected; **Close** and **Reopen**. |
| **Backups** | admin | When the last backup was made, whether it worked, encrypted or not, whether there is a second copy, the files on disk, and **Back up now**. |
| **Staff** | admin | HQ's accounts: add a person with a temporary password and a role (viewer, catalog, HR, payroll, admin), change a role, set a new temporary password, close or reopen an account. You cannot change your own role or close yourself. |
| **People** | any staff read; HR and admin change | Everyone who works in the chain with where they work. HR adds a person (code, name, branches), ticks the branches, sets the **attendance PIN** (typed once in a box, never shown again), gives an employee a **sign-in** (a name and a temporary password), and marks who has left. A person with no sign-in (a cleaner) is normal. |
| **Attendance** | any staff read; HR and admin correct | The days in a period by branch or person: each clock-in and clock-out, the hours worked, and a red flag where a punch is missing (clocked in twice, out without in, still in). HR **adds a missed punch** or **cancels** one, always with a reason that is kept; a punch a branch recorded is never edited. |
| **Payroll** | payroll and admin | The runs, then one run at a time: where it is (draft, calculated, approved, paid, locked) with what to do next, the warnings, the totals, every payslip (days, hours, gross, deductions, net; **Lines** shows each line; **Print** opens the payslip page through a one-use link), and the run's **extra lines** (a bonus or a deduction for one person). Approving and paying ask "are you sure": after approval the figures are frozen. A refusal from HQ (a branch has not caught up, the period is not finished, no exchange rate) is shown in its own words. |
| **Pay setup** | payroll and admin | How each person is paid (monthly, daily or hourly, in LBP or USD, overtime, the rules that apply), the dated **rules** (NSSF, tax: a percent with an optional cap, or brackets) and **loans**. Nothing is edited: a change is a new row from a day on, and the older rows stay shown. |
| **Schedule** | any staff read; HR and admin change | Four tabs. **Roster:** a week for one branch, a row per person assigned there and a day per column; each cell is a shift or "off", saved as soon as it is chosen (so the roster is a plan that can be changed, every change audited), with holidays marked in the header and **Copy last week**. **Plan and what happened:** for a period, each rostered day as worked, absent, on leave, a holiday or not on the roster, with late and left-early minutes and totals (planned and worked time, absent and leave days); a day not yet over is "still to come", never an absence. **Leave:** requests with approve, reject and cancel (an approved leave that overlaps another is refused), a form to record one, and the kinds of leave (paid or unpaid). **Shifts and holidays:** shifts with their hours (a night shift shows "(next day)"), retired rather than deleted so old rosters keep their meaning, and holidays. Times are typed as hh:mm and read exactly; a time that is not a time cannot be sent. A viewer reads all four and is offered no button to change anything. |
| **Purchasing** | any staff read; catalog and admin make and place; admin pays | HQ's orders to suppliers, delivered to stock branches. The list shows **what HQ owes each supplier** and every order with its state and what is still to pay. **New order** (a draft): supplier, currency, note and lines found by name or barcode, each line going to a stock branch with a quantity (up to three decimals) and a unit cost (filled from the product's cost when the currencies agree); it is **saved as a draft and nothing is ordered**. An order opens to its lines (ordered, arrived, cost, value) and four totals (ordered, arrived, paid, still to pay). A draft can be **changed** (the whole draft is replaced) and **placed** (each stock branch is then told what to expect; the lines are frozen); a placed order can be **closed** (accept what arrived) and a draft or a not-yet-delivered order **cancelled**, each after an "are you sure". **Pay the supplier** (admin, for a placed or closed order): an amount in the order's currency, part payments are fine, more than is owed is refused in HQ's words; one `Idempotency-Key` per attempt, kept until the payment goes through, so a repeated send is one payment. A viewer reads all of it and is offered no button. |
| **Stock suggestions** | any staff read; catalog and admin can make a draft | Three tabs, each with a branch filter, and a line saying HQ only suggests. **What to buy:** stock branches at or under a product's alert, counting what is on the way and already ordered; the suggestion brings it to twice the alert, and "shops could not get" shows what shops asked for in the last 30 days that no stock branch could supply. Rows can be chosen and turned into **one draft order** (each line to the branch that is short, at the product's own cost; products priced in different currencies are refused, since an order has one) which opens for review. **Slow shops** (stock lasts longer than the slow days: send back) and **Fast shops** (lasts the fast days or less: ask a stock branch for more): the numbers of days can be changed and are checked (whole numbers 1 to 365) before anything is asked. Stock never moves shop to shop. |
| **My pay** | employee accounts | An employee's whole screen: their own paid payslips (opened through a one-use print link) and their own attendance for two weeks. Nothing else is reachable: it is read through `/me`. |

The server decides who may do what (docs/16 §7); the screen only hides the buttons a person cannot use. An amount typed on a form is turned into whole lira or cents by exact text parsing (`parseMinor`, `parseBp`: no floating point, a fraction of a lira or a third decimal is refused before it is sent). Amounts are shown on these pages only: nothing about pay goes into a log, an alert or a URL.

## 3. How it handles the sign-in

The session token (`POST /auth/login`) is kept in `sessionStorage` (gone when the tab is closed, never written to disk by the page) and sent only to HQ, in a header. HQ no longer accepting it (expired after eight hours, signed out elsewhere, role changed) sends the person back to the sign-in page with nothing of the last person left on screen. The one-time branch code lives only in the page's memory and is not stored anywhere.

## 4. Tests

`cloud-hq/tests/web.test.ts` (serving, headers, the router fallback, traversal, the API's strict headers, the payslip page keeping its style), `cloud-hq/tests/unit/screen-format.test.ts` (the figures and sentences the screen shows, and the exact parsing of typed amounts and percentages), and the payroll system test checks a run lists its manual lines. **The pages themselves were checked in a real browser by a script** (for the HR and payroll pages: add a person with a branch, set a PIN and see it is not shown anywhere, give a sign-in, add a rule and a pay, refuse a fractional lira, add a missed clock-in and clock-out and see 8 h 00, start a run, calculate, see the NSSF line, add and remove an extra line, approve, pay, lock, print a payslip, then sign in as the employee, choose a password and see only their own payslip and no menu; no console errors). Earlier:  (sign in with a wrong and a right password, add a branch and see its code, Overview, Staff, Backups, reload stays signed in, sign out; no errors in the console but the expected 401), **and the same flows are now kept as browser tests** (below).

**Browser tests (`npm run e2e --prefix cloud-hq`, or `npm run test:e2e:hq` at the top):** Playwright, in `cloud-hq/tests/e2e`. `playwright.config.ts` builds the screen and starts `src/cli/e2e-server.ts`, a throwaway HQ (temporary data folder that is deleted when it stops, one admin, never reads `DATABASE_PATH`, so it cannot touch real data), then drives Chromium against it. `purchasing.spec.ts` (8, makes its own stock branch, supplier and products): what to buy lists what is short with the right suggestion and a product with no alert is left out; chosen rows become a draft; a draft is changed (a quantity, a supplier, a product found by search) and a four-decimal quantity cannot be saved; placing freezes the lines and the suggestions stop asking for what is on order; a part payment lowers what is owed, more than is owed is refused, and the list shows what HQ owes; a new order from scratch is cancelled; the days of the slow and fast tabs are checked; a viewer reads everything and is offered no way to change or pay. `schedule.spec.ts` (5, makes its own shop and person): a day and a night shift are added and a bad time cannot be sent; shifts are set per day and kept, and a week is copied to the next; a rostered day that is over with no punches is an absence, approved leave turns it into leave and cancelling it brings the absence back; a holiday on that day is not an absence and removing it brings the absence back. `screen.spec.ts` (6): a wrong and a right password and a reload; the page policy and where the token lives; adding a branch shows its one-time code once and it is gone when the page is left; the backups page; a viewer is stopped at "choose your password", sees no admin or pay page and is sent home from `/payroll`; signing out. `hr-payroll.spec.ts` (6, in order): one person from added to paid (the attendance PIN typed once and never in the page, a sign-in, a rule and a pay, a fraction of a lira that cannot be sent, a missed punch added with a reason and 8 h 00 worked, a run calculated with its NSSF line, an extra line added and removed, approve, pay, lock, a locked run that offers nothing, the payslip page), then the employee reads only their own payslip and attendance with no menu. **Every test fails on any script error or console error** except the ones a refused request causes by itself (a 4xx the screen explains). It needs the browsers Playwright installs (`npx playwright install chromium`), takes about 15 seconds, and is not part of `npm test`.
