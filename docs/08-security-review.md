# 08 · Security review

A review of the whole system as it stands at the end of M5, done by reading the code, running probes against the running server, and turning every check that can be automated into a test so it cannot quietly stop being true. It is a review by the people who built it. **It is not a penetration test by an outside party**, and section 4 lists what it did not cover.

The threat model is a single shop PC: the server listens on this PC only, one browser uses it, the people who can reach it are the shop's staff, and the data worth protecting is sales, customer balances, and staff passwords.

## 1. What was found and fixed

| # | Finding | Why it mattered | Fix | Test |
|---|---|---|---|---|
| 1 | **A PIN opened any account that had one.** The PIN sign-in worked for managers and admins too (US-25 says cashiers). A 4-digit PIN would have guarded an admin session | A short secret guarding the most powerful account | PIN sign-in is for cashiers only. The PIN screen lists only cashiers. A manager or admin cannot be given a PIN (`422 PIN_CASHIER_ONLY`), promoting a cashier removes their PIN, and a PIN already stored on a manager (an old account) does not sign in | `security`: three tests, including a manager whose PIN was written straight into the database |
| 2 | **The server answered to any name.** A web page on the internet can point its own name at 127.0.0.1 ("DNS rebinding") and talk to the server from the shop's browser | Cross-site access to a server that was meant to be private to the PC | Requests whose `Host` is not `localhost`, `127.0.0.1` or `[::1]` (plus names listed in `ALLOWED_HOSTS`) get `403 HOST_NOT_ALLOWED`. A request with an `Origin` from another site, or one that cannot be read, gets `403 ORIGIN_NOT_ALLOWED`. No CORS headers are ever sent | `security`: five tests |
| 3 | **No browser security headers** | A page could be framed by another site, scripts could be injected, the address leaked in the Referer | Every answer carries a Content-Security-Policy (own scripts only, no inline script, no `eval`, no framing, no plugins), `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `nosniff`, cross-origin isolation headers | `security` (headers) and **`production-build`** browser tests: a whole shift, a refresh on a page, a CSV download and a cookie session all run under the policy with **zero** violations; an injected inline script is blocked and recorded; a product named `<img onerror=…><script>…` is shown as text and runs nothing |
| 4 | **Two critical and one moderate advisory in the test tooling** (vitest, tinypool) | Dev-only (`npm audit --omit=dev` was already clean), but a developer's PC runs the tests | Upgraded vitest 3 → 5. Audit now reports 0 vulnerabilities; the whole unit, integration and migration suites pass on the new version | CI now runs `npm audit --omit=dev --audit-level=high` |

## 2. What was checked and found sound

| Area | Result | Where it is proven |
|---|---|---|
| **Every route is guarded** | Every one of the server's routes except six deliberate ones (`healthz`, `readyz`, `login`, `pin`, `refresh`, `logout`) refuses a request with no token or a garbage token. The test lists the routes the server actually registered, so **a new route that forgets its guard fails the build**. The check was shown to bite by adding an unguarded route on purpose | `security` |
| Tokens | A token with no signature (`alg: none`) and one signed with another secret are refused. The access token carries only the user id; the role and "active" are read from the database on every request, so deactivating or demoting someone takes effect at once | `security`, `auth-session` |
| Passwords and PINs | Argon2id (19 MiB, 2 passes, the OWASP minimum). Unknown user and wrong password take the same time and give the same answer. Hashes never leave the server | `auth-*`, `security` |
| Lockout | 5 failures lock an account for 15 minutes, separately for passwords and PINs. Changing the capital letters of the username does not dodge it | `security`, `auth-session` |
| Sessions | The refresh token is a random value kept only as a hash, in an httpOnly, SameSite=Strict cookie limited to `/api/v1/auth`. It rotates on every use; presenting an old one revokes every session of that user (theft detection) | `auth-session` |
| SQL injection | Every statement passes values as parameters. The statements that build text (column or table names) take them from fixed lists, never from the request. Search boxes, barcodes, names and ids were attacked with SQL, quotes, wildcards and full-text operators: nothing was returned beyond rows, nothing was damaged, and no database error text came back | `security`, `products` |
| Malformed and huge input | Broken JSON is a plain 400 with no stack trace; a 2 MB body is refused with 413; non-numeric ids never reach the database as anything else | `security` |
| Cross-site scripting | React escapes everything; there is no `dangerouslySetInnerHTML`, `innerHTML` or `eval` in the web app. The browser-print window writes the receipt with `textContent`. Spreadsheet downloads neutralise text that could run as a formula | `production-build`, `web/csv` |
| Secrets in logs | The real log output of a login, a failed login, a PIN sign-in, a refresh, a password change and a backup was captured: no password, PIN, token, cookie or backup passphrase appears, and no `Authorization` or cookie header | `security` |
| Secrets in answers | No password, PIN, hash, token secret or passphrase in the users, session, settings, audit or backup answers | `security`, `backup` |
| History cannot be rewritten | Sales, payments, stock movements, cash movements and the audit log are protected by database triggers, not only by the code | `db/schema` |
| Serving the app | Files outside the web folder cannot be read (`..`, encoded and doubled forms were tried); hashed assets are cached, pages never are; API answers are never cached | `static-web` |
| Backups | Encrypted with AES-256-GCM (a wrong passphrase, a flipped byte and a cut-off file are all detected); a restore changes nothing until the file has been checked | `backup`, `backup-cli` |

### Added after the review: manager approval for discounts (US-09)

Built after the review above and reviewed the same way (`tests/integration/approvals.test.ts`, 20 tests):

- It is **not a PIN.** A manager types their own name and password at the cashier's till (rule 20 stands). A cashier's password, a wrong password, an inactive account and an unknown name all get the same refusal.
- **The approval is bound to what the manager was shown.** The first design carried only "a manager said yes", which would have let a cashier get approval for a small discount and send a large one. The token now holds the percent that was approved; a bigger discount is refused and does not use the approval up. This was found while building the till screen and fixed before it shipped.
- It works **once**, for **one cashier**, for **ten minutes**, and is used inside the sale's own transaction, so a sale that fails for another reason does not burn it, and a retry replays the sale instead of needing a second approval.
- Wrong attempts are counted **apart from sign-in**, so a cashier guessing cannot lock a manager out of signing in. (They can lock approvals for that manager for 15 minutes: the same kind of nuisance as risk 4.)
- Only a hash of the token is stored; the token and the manager's password never reach the log (checked by the log test).
- **Service worker:** it is a file of ours served from the same origin (allowed by `script-src 'self'`), re-checked on every visit (`no-cache`), and it never handles `/api`, so no token, cookie or money figure is ever stored by it. It keeps only the app's own files and product pictures. A new build gets a new cache name and the old one is deleted.
- **Offline:** an approval is checked by the server, so a discount that needed one cannot be queued offline. The till says so.
- **Returns now use the same approval** (US-14, `tests/integration/return-approvals.test.ts`, 13 tests). A cashier may start a return, but the server refuses it (`RETURN_NEEDS_APPROVAL`) unless it carries a token for **that sale** that covers **the value the server computed and the manager was shown**. Same rules as above: once, one cashier, ten minutes, used inside the return's transaction (a return that then fails does not burn it), a discount token cannot be used for a return or the other way round, and the grant and the return are audited (`approval.grant`, `sale.return` with `approvedBy`) without any secret. Why it matters: a return hands cash out of the drawer, so it is the easiest way for a cashier to take money; before this the only safe route was a manager signing in at the till, which in practice meant managers stayed signed in. Residual risk: a manager who approves without looking at the amount shown. The amount is on the dialog and in the audit trail.
- **Void and price override now use it too** (`tests/integration/void-price.test.ts`, 20 tests). A **void** approval is for one sale; a **price** approval is for one product at exactly one unit price in whole lira; both work once, for one cashier, for ten minutes, are used inside the sale's (or void's) transaction, and a discount, return, void or price token cannot be used for another scope. A cashier can only cancel a sale while its register is open (after the count it is settled: a return is the way back). A void needs a reason and is audited with who approved; a price override is audited with before, after and who approved. Residual risk: a manager approving without reading the dialog. The amount or price is on the dialog and in the audit trail.
- **A first password is now refused by the server for everything but changing it** (`PASSWORD_RESET_REQUIRED`), not only by the screen: the earlier note that it was a convenience is superseded. `GET /me` and `POST /auth/change-password` are the only routes a person in that state can use.
- **HTTPS (optional, for a tablet or second PC):** set `TLS_CERT` and `TLS_KEY`; the server then answers HTTPS only, marks the sign-in cookie `Secure` and sends `Strict-Transport-Security` (`tests/integration/tls.test.ts`). The certificate is the shop's own (a self-signed one must be trusted on the tablet; `docs/07-operations.md` has the commands). Risk 2 (credentials crossing the Wi-Fi in the clear) is closed **only for a tablet that uses it**; `HOST` and `ALLOWED_HOSTS` without TLS remain unsafe and the documentation says so.
- **Cashier PIN switch at the till:** the PIN screen only lists cashiers who have a PIN, only a cashier's PIN opens a session (a manager's never does, even if one was left on the account), the lockout counts per user, and a wrong PIN counts as one try. The cart stays with the till.
- **Stocktake, services and duplicate-barcode tools** are manager-only, validated with Zod, audited, and follow the append-only rules (finished counts and service records are frozen by triggers; merging hides products and moves stock instead of rewriting history).

### Added after the review: product pictures (US-15)

The pictures feature came with the one thing this review had flagged as needing its own look ("code not written yet: image upload"). Reviewed the same way (`tests/unit/images.test.ts`, `tests/integration/images.test.ts`, the importer tests, `tests/e2e-prod`):

- **A picture is judged by its bytes**, never by its name or the type the sender claims. This mattered on day one: the legacy `Uploads` folder has a `.png` that is WebP, a `.jpg` that is AVIF, and **two saved web pages (`.htm`, `.html`)** sitting among the pictures, and two products point at those pages. Anything that is not JPEG, PNG, GIF, WebP or AVIF is refused. **SVG is refused on purpose** (it can carry a script).
- **The public route `/uploads/<name>` serves only the exact names the server makes** (24 hex digits and a picture extension). A web page placed in the folder by hand, `index.html`, the database file next to it, `..` in any spelling, a wrong extension, capitals: all `404` (tested, including a hand-placed `.html` with a name of the right shape). It is public because an `<img>` cannot send a sign-in and the pictures are not secret; the Host and Origin checks still apply. It is the one route outside `/api/v1`, so the route-guard test does not list it: this is where it is accounted for.
- **Content-named files:** the same picture is stored once, a name never changes meaning, so it can be cached for good, and an upload can never overwrite another picture.
- **Limits:** 5 MB, one picture per request, managers only, audited (old and new path). The importer refuses to write into the folder it reads from.
- **The Content-Security-Policy already allowed `img-src 'self'`**; a browser test shows a picture loading under it with no violation.
- **Not done / residual risk:** pictures are not re-encoded or scanned, so a deliberately corrupted image could still try to exploit a flaw in the browser's own decoder; only managers can upload, and the browser is kept updated like any other. The pictures folder is not encrypted, in the PC or in the backups. Old pictures are never deleted from disk (a replaced one stays): the folder only grows.

### Added after the review: reprints and sales waiting on a till (US-06, US-10)

- **A reprint cannot pass for the original, and cannot be a way to open the drawer.** Only the first print that reached the printer may open the cash drawer; every later one is stamped DUPLICATE (top and bottom) and keeps the drawer shut even if the till asks. Each print is audited with who printed it. This closes a small fraud route: a reprinted receipt used to be indistinguishable from the first, and "print again" used to pulse the drawer. A browser print cannot be seen by the server, so it is not recorded (it is stamped when it comes from the sales screen).
- **A sale waiting on a till is money that is not in the system yet.** The sales screen lists every one, with the reason the server gave if it refused it. It can leave the list in two ways only: the server records it, or **a manager** discards it, which asks why, says what it means, and tells the server, which keeps a note (`sale.queued.discard`: who, what, why). A cashier cannot discard. The server refuses to note a discard for a sale it did record (the answer may have been lost on the way back); the till then just sends it again.
- **Residual risk:** the waiting sales live in the browser's own storage on that PC. Someone who can clear that browser's data (or uses another browser profile) could remove a waiting sale without the server hearing of it. It needs access to the shop PC's signed-in desktop, and the sale was never in the register's expected figures, so the closing count would show the difference.

## 3. Known risks that are **not** fixed (read these)

1. **The server runs as the Windows SYSTEM account** (the install script does this so it can start before anyone signs in and reach the printer). If the server were ever compromised, the attacker would have the most powerful account on the PC. A dedicated low-privilege account would be better. It was **not** changed, because it cannot be tested here and a mistake would break printing or backups on the day of the install. Do it deliberately, with the real printer and backup drive in front of you.
2. **No encryption in transit (no HTTPS).** On the PC itself this is fine: the traffic never leaves it. **Do not let a tablet or another PC connect over Wi-Fi** (`HOST=0.0.0.0` with `ALLOWED_HOSTS`) until HTTPS is set up: the sign-in and the session would travel in the clear. `ALLOWED_HOSTS` only decides which names are answered; it is not a substitute.
3. **A cashier can open any sale by its number, and can see the list of customers with their balances** (a cashier's own sales *list* is limited to their own). The till needs both (returns, credit). It is by design, and a decision for the owner if it is not wanted.
4. **Anyone who can reach the sign-in screen can lock a user out** for 15 minutes by typing five wrong passwords. It needs access to the till, and it expires by itself.
5. **Idempotency keys are not tied to the user who sent them.** They are random UUIDs, so guessing one is not feasible, but a leaked key could replay the stored answer to someone else.
6. **Password rules are modest:** 8 characters, no check against lists of common passwords. The two imported users have no password until the owner sets one.
7. **The backup passphrase is stored in `C:\POS\service.env`**, readable by administrators and the server. Someone with an administrator account on the PC who also has a backup file could decrypt it. That is the trade for backups that run by themselves; the copy on the external drive is encrypted, and the passphrase should be on paper away from the PC.
8. **Rate limiting** of the sign-in endpoints is on in production only (10 a minute per address); the account lockout above applies everywhere.

## 4. What this review did not cover

- **An outside penetration test.** None was done.
- **The Windows PC itself:** who has an account on it, updates, antivirus, disk encryption (BitLocker), what happens if someone plugs in a USB stick or takes the PC. The data on the disk is not encrypted; a stolen PC means stolen data unless the disk is.
- **The real printer and the SYSTEM-account printing path**, on a real till PC (see `docs/07-operations.md`).
- **Users screen and first sign-in (added at cut-over, `tests/e2e/users.spec.ts`):** admin only on the server (it always was) and now in the UI. A first password given by the admin can be marked "must choose their own"; the UI then stops that person on a *Choose your password* page before anything else, and the old password stops working once they have. **That stop is in the UI only**: the server accepts the first password for everything until it is changed. It is a convenience so the admin never learns the final password, not a security boundary. An admin cannot switch themselves off or demote themselves (the server refuses), so the shop always keeps one admin. Managers and admins have no PIN.
- **Product CSV import (reviewed when built, `tests/integration/product-import.test.ts`):** manager or admin only, validated with Zod, at most 3 MB and 5,000 products. The file is text, never run: a cell that looks like a spreadsheet formula (`=HYPERLINK(...)`) is stored as plain text, and the CSV export already neutralises such cells when they are written back out. All SQL is parameterised (list names are matched with bound values; table names come from a fixed list in the code). Money is read exactly (no floats, no guessing). One transaction, so a crash cannot leave a half-imported file, and every change is audited per product with `via: import`. Residual risk: a manager can change many prices at once with one file. The preview shows every changed row first, and the audit log keeps before and after for each price.
- **The code of third-party packages** beyond `npm audit`.
- **Resilience to a determined flood of requests.** The server is not reachable from outside the PC by default.

## 5. Keeping it true

- `tests/integration/security.test.ts` fails if a route is added without a sign-in guard, if a secret reaches the log, if the headers or the address checks change, or if the PIN rule loosens.
- `tests/e2e-prod/` runs the built app under the real policy; a change that needs an inline script or a foreign origin fails there.
- Run `npm audit --omit=dev` after every dependency change (CI does).
- A new public route must be added to the allow-list in `security.test.ts` on purpose, with a reason in the commit.
