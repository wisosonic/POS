# CLAUDE.md

Guidance for Claude Code and other AI assistants working in this repository.

## Project

Market POS, first built for Darwish Market (Beirut), replacing a legacy ASP.NET + SQL Server app. **It is now becoming a chain system for a fresh customer (2026-11-24): the legacy Darwish system stays separate, nothing here has to migrate its data, and each customer gets a separate install.** React PWA front end, Fastify + TypeScript API, SQLite (`better-sqlite3`).
The full design is in `docs/`. **Read the relevant doc before changing a related area, and update the doc when behaviour changes.**
Deployment: a Windows PC runs the API (which owns the SQLite file); the tills are browsers, on that same PC or on others, and a till whose printer is elsewhere runs a print agent (`docs/04-architecture.md` §1, `docs/07-operations.md`). Current state: the single-branch system is built and tested (milestones in `docs/plan.md`), with several tills per branch; it has **not** been run on a real till PC yet. The multi-branch / HQ plan is in `docs/PLAN-MULTI-BRANCH.md`.
**Growing into a chain (multi-branch, HR, online shop) is planned in `docs/PLAN-MULTI-BRANCH.md` (architecture in `docs/11-multi-branch.md`). Read it before touching the database layer, registers, sync or users, and update its Progress section at the end of every piece of work.** Until a phase there says otherwise, the one-till rules below still hold.

**Planned (decided 2026-11-27, not built; `docs/14-connection-and-till-backend.md`):** a till stops selling while the branch server is unreachable (no offline queue), a ping replaces the live-update stream, the till's Node backend keeps a read-only copy of the items on disk, and sign-in stays a JWT on the branch server. Until a step there is built, the rules below describe the system as it is (the browser queue and `/events` still exist).

## Layout (docs/11-multi-branch.md §8.2, §8.3)

Five project folders, each complete and able to run alone on its own machine; the top level holds only `docs/`, `scripts/`, `legacy/` and the plan files.

```
till/            the till: web/ (screens), agent/ (the till's own server: serves the screens and passes calls to the branch server; the print agent; the sales queue is still in the browser), shared/ (COPY of branch-server/shared)
branch-server/   the branch's server (src/), core/ (database layer), shared/ (MASTER of money, pricing, barcode, receipt), tests/, data/ and backups/ (not in git)
cloud-hq/        the HQ server (src/), core/ (HQ's own copy of the database layer), tests/ (incl. tests/system: HQ with two branches)
marketplace/, mobile-app/   not built yet (placeholders)
legacy/          the old Darwish data and tools (POSDB.sql, Uploads/, old data/); not part of any project
```

- **Each project has its own `node_modules`.** `npm run setup` (top level) installs all four, or `npm install` inside one project. Run a project's commands from its folder or with `npm --prefix <project> run <script>`. The top level's scripts are shortcuts, and the top level has no `node_modules` of its own.
- **Code style is per project too:** each project has its own `eslint.config.js`, `.prettierrc.json`, `.prettierignore`, `.editorconfig` and its own `lint`, `format`, `format:check` scripts (the shared part is copied, like `shared/`: change one, change all three). The adapter lint rules are in `branch-server/eslint.config.js`. `scripts/` is not linted.
- **No project imports another project.** The one exception, for now: `cloud-hq/tests/system` and `till/agent/tests/system` import the branch server's code; they become process-based later.
- **Copies:** `till/shared` is copied from `branch-server/shared` (the master): change the master, copy the files, run both projects' tests. `cloud-hq/core` is HQ's own copy of the database layer and may diverge. `till/agent/src/printer.ts` is the agent's copy of `branch-server/core/src/printer.ts`. The check that copies match is not written yet.
- `node scripts/check-alone.mjs` starts each server alone from its own folder and checks it answers. `npm run test:sandbox` (`scripts/sandbox-chain.mjs`) goes further: each project is copied alone into its own temp folder, installed and run there, and the whole chain (HQ, two branches, a till) is driven over HTTP (docs/11 §8.5). It needs the internet and about two minutes; run it after changing anything a project shares with another (sync format, `shared/`, the till server).

## Hard rules

1. **Money is integers.** LBP in whole LBP, USD in cents. Never use `float`/`number` fractions for money. Never parse money from strings except in the ETL and the product CSV import, and fail loudly there (the import uses `parseDecimalMinor` from `branch-server/shared`: exact, no floats, refuses commas, signs and extra decimals). Each product has its **own currency**. The cart converts to LBP at the current rate.
   **There is no tax.** Selling prices are tax-inclusive. Do not add tax fields, settings or receipt lines.
2. **The server decides totals.** Recompute from catalog prices and the rate. Never trust client-sent totals.
3. **One DB transaction per sale** covering sale, items, payments, stock movements, customer balance, register balances and audit, via `inWriteTransaction` (`BEGIN IMMEDIATE`). Never write outside it. Only the API process may open the database for writing.
4. **History is append-only.** Never UPDATE or DELETE sales, payments, stock movements or audit rows. Corrections are new rows (returns, adjustments, voids). The database enforces this with triggers (migration 0001), so a violation throws.
   **One exception, by the owner's decision (docs/QUESTIONS.md #8, option C):** a cancelled sale, or a sale that has had items taken back, can be deleted for good through `POST /sales/{id}/delete` (`modules/sales/delete.ts`, migration 0014). That is the only code that deletes these rows. The triggers let a sale's own rows go only while `sale_delete_unlock` holds a row for that sale, which the routine inserts and removes inside its one transaction. It reverses the stock, recomputes the register's expected figures (a counted register's variance changes) and lowers the customer's balance in that same transaction, and the audit log (never deletable) keeps what the sale was and who deleted it. Do not add another delete path, and never leave a row in `sale_delete_unlock`.
   **SQLite rules:** quantities are integer thousandths (`qty_milli`), never floats. Use `openDatabase()` so WAL, `synchronous=FULL` and `foreign_keys=ON` are set. Schema changes are new numbered `.sql` files in `branch-server/src/db/migrations/`. Never edit an applied migration.
5. **Stock = ledger.** Change stock only by inserting `stock_movements`. `stock_levels` is a cache updated in the same transaction.
6. **Idempotency** on `POST /sales`, `/returns`, `/customers/{id}/payments`, `/purchases/{id}/receive`.
7. **A printer failure must never fail or roll back a sale.** The printer is USB and **English/ASCII only**: receipts use `receipt_name`, which is auto-transliterated from Arabic names (`branch-server/shared/translit`). Only truly unprintable characters print as `?`.
8. **Barcode checksums are advisory.** Legacy codes include EAN-8 and arbitrary numbers, so lookups must accept any string.
9. **Exchange rate is snapshotted per sale.** Never recompute historical totals with the current rate.
10. **Validate every input with Zod.** Parameterized SQL only. No string-built queries.
11. **Never log or return password hashes, PINs or tokens.** Argon2id for passwords.
12. **Shared domain logic lives in `branch-server/shared`** (money, pricing, barcode, receipt) so client and server cannot drift.
13. **Payment methods are `cash`, `whish`, `omt`, recorded only.** Never call a third-party service. Change is always cash. A wallet tender may not exceed the amount due.
14. **Cash belongs to each till, wallets belong to the branch** (docs/13-branch-wallets.md). A payment method has a `holder` (`payment_methods.holder`: cash = `till`, Whish and OMT = `branch`). A register session's balances are the **till buckets** (method × currency for methods a till holds: today `cash/LBP` and `cash/USD`); open and close require all of them and refuse any other. A wallet (holder `branch`) is a **ledger**, `wallet_entries` (append-only, signed amounts, written in the SAME transaction as what caused it, never edited: a void or a deleted sale adds a `correction`), with manager counts in `wallet_counts`; its expected balance is the latest count plus the entries after its `entry_mark`. Everything that moves money calls `bumpExpected(q, sessionId, bucket, delta, cause)`: a till bucket updates the session, a wallet bucket becomes a ledger entry and **a wallet change without a `cause` throws**. Old sessions keep the six balances they had (history is not rewritten). `walletLedgerCheck` re-derives each wallet from the source rows: keep it green. Built so far: the ledger, routing, till screens and the manager-only wallet routes (`/wallets`, `/wallets/counts`, `/wallets/movements`, `/wallets/entries`; a count is never required and never blocks selling); the Wallets page (Money menu), the dashboard tile and reminder, and the blind-count shop setting (`store_settings.cashier_blind_count`, default on: the server sends a cashier `expected: null` for an open register; managers always see it) are built too (docs/13 §10, slices 1 to 4: all built; the Cash page shows the wallet side of a transfer).
15. **Credit needs a registered customer.** Partial or unpaid sales are rejected for Walk-In (`customers.is_walk_in`, id 1). Invariant: `customer.balance = Σ open sales.rest`. Customer payments are applied to the oldest open sale first.
16. **Several tills per branch, one register each.** One open register session per terminal, and any logged-in user may sell in the session of the till they are on. A till is identified by its **device token** (`X-Terminal-Token`, made by admin enrolment with a one-time code, stored only as a hash, never logged); the server never trusts a client-sent till name. Routes that need a register or warehouse use `preHandler: [app.authenticate, app.withTerminal]` and `req.terminal`. **Legacy single-till mode:** with exactly one active terminal and none enrolled, a request with no token is that terminal, so a shop that has not set terminals up works as before. A terminal sells from its own warehouse (`warehouseOf`), else the first. Sales record `user_id` and `session_id` (and so the terminal). See `docs/11-multi-branch.md` §3.4. **In the web app** the token lives in `localStorage` (`lib/terminal.ts`, memory if storage is blocked) and `lib/api.ts` sends it on every request, queued sales included; a `401 TERMINAL_UNKNOWN` clears it and must never sign the person out (it is not a lost sign-in). A device the server does not know shows `DeviceNotATill` instead of the till (`isNotATill`); an admin enrols it there or in Settings → Tills.
17. **Stock never blocks a sale or a purchase.** Its purpose is notifying the owner when a product is low: each product has its own `stock_alert` threshold (null = no alert). Quantity may be 0 or negative. Do not add stock checks, stock errors or override flags to the sale or purchase flows.
18. **Barcodes are unique only once the rule is switched on.** The legacy data has shared barcodes, so lookups can return several products and the rule starts OFF. Menu → Duplicate barcodes cleans them up (re-code, or fold products into one with `POST /products/merge`) and then turns on `store_settings.barcode_unique`, after which triggers (migration 0010) refuse a second **active** product with the same barcode (`DUPLICATE_BARCODE`). A hidden product may keep a code. Never rewrite sale history to merge products: retire them and move the stock.
19. **Every route needs a sign-in guard** (`preHandler: app.authenticate` or `app.requireRole(...)`). `branch-server/tests/integration/security.test.ts` lists the routes the server registered and fails for any that answers an anonymous request. The only open doors are the six in its allow-list: add one only on purpose.
20. **A PIN is cashier-only.** Managers and admins sign in with a password. Never lift that. A manager's approval at the till (over-limit discount) is their **name and password** → `POST /auth/approve` → a token that is single-use, for one cashier, up to the percent the manager was shown, for ten minutes, used inside the sale's transaction. Never make it a PIN, never make it reusable, and never let it cover more than was shown. The same token mechanism covers a **cashier's return** (`scope: "return"`: bound to one sale and the value in LBP the server computed; `RETURN_NEEDS_APPROVAL` carries that value so the screen can show it). The scopes are `discount` (a percent), `return` (one sale and a value), `void` (one sale), `delete` (one sale, to delete it for good) and `price` (one product at one unit price). A new thing a cashier may do only with approval gets its own scope, bound to what the manager saw, and is consumed inside the transaction. Add it to the `approvals` table's CHECK with a migration (the table is rebuilt, as in 0006 and 0007).
21. **Never put a secret in a log line, an error or an answer** (password, PIN, token, cookie, backup passphrase). The security test captures the real log and fails if one appears.
22. **No inline scripts, no `eval`, no foreign origins.** The Content-Security-Policy is `script-src 'self'`. Styles may be inline (React writes `style=""`). The `production-build` e2e project runs the built app under the real policy.

## Pitfalls already hit (do not repeat)

- **Two servers, each with its own copy of the core.** The branch server (`branch-server/core`, the original) and the HQ server (`cloud-hq/core`, its own copy that may diverge; docs/12-sync-and-hq.md) each have a local `@pos/core` package: the database adapter and SQLite driver, the migrations runner (`migrateFrom(dir, target)`, each server has its OWN migrations folder and database), errors, validation and the credential helpers. The old paths in `branch-server` (`db/adapter`, `db/open`, `errors`, ...) are one-line re-exports: new code may import `@pos/core/...` directly. A new local package needs `npm install` in its project (it links `node_modules/@pos/<name>`); without the link, tests fail with `Cannot find package '@pos/...'`. The sync lists (`core/src/sync.ts`) exist in both copies: change both and keep `cloud-hq/tests/system/sync-schema.test.ts` green.
- **HQ is the first internet-facing part.** Its open doors are `/healthz` and `/sync/enrol` only (the one-time code is the credential); `cloud-hq/tests/hq.test.ts` proves every other route refuses an anonymous request and a garbage token. A branch signs in with `X-Branch-Token` (never a person's sign-in), HQ staff with the interim `HQ_ADMIN_TOKEN` (replaced by HQ users in P3). Codes and tokens are stored only as hashes, shown once, and never reach a log, an audit row or an answer. The branch keeps ITS token in `hq_link` and never returns it.
- **The sync loop is background work that must never block a sale or a shutdown.** `modules/sync/agent.ts` only ever uses short transactions, does its network calls OUTSIDE any transaction, never throws out of its loop, and stops in `preClose` (like the SSE stream and the print agent's long poll). The first success after an outage calls `onReconnect`: that is where data sync plugs in.
- **What goes up to HQ is listed once, in `branch-server/core/src/sync.ts`** (docs/12 §14). A new column on `sales`, `sale_items`, `payments` or `stock_movements` needs the list, HQ's mirror table (a new HQ migration) and, for a new synced table, three capture triggers in a new branch migration; `branch-server/tests/db/sync-schema.test.ts` fails until all agree. The capture triggers (migration 0018) write the branch's `sync_outbox` only while `sync_control.capture = 1` (connected); never write to the outbox by hand, and never clear it except after HQ's OK. HQ stores rows by upsert keyed `(branch_id, id)` and takes the branch id from the token only. **Going down** (HQ-owned data, `DOWN_TABLES`): HQ writes a `change_log` line in the same transaction as the change (in code, not a trigger); the branch applies a whole page plus its `down_cursor` in one transaction, keeps HQ's id in `hq_id`, and never edits an HQ-owned row itself while connected (the rate route answers `HQ_OWNS_RATES`). **Server-side watchers of the event bus use `events.tap`, not `subscribe`:** `subscribe` counts as a listening screen (`events.size`, which a test checks).

- **Live updates (`events/bus.ts`, `GET /events`).** Events are hints with no data (`{ type, at }`); a screen asks for the real thing through the normal calls and refreshes everything after a reconnect. They are published from one place, the `onResponse` hook in `app.ts`, from the route pattern and the status (`eventsFor`), so a new route that changes what other screens show needs a line there. **Anything that holds a connection open must be ended in a `preClose` hook, not `onClose`** (Fastify runs `onClose` only after the server has finished waiting for its connections, so the server hangs): the SSE stream destroys its sockets and the agent's long poll answers at once. A test starts a server with a stream open and closes it.

- **The print agent (`till/agent/src/agent.ts`, migration 0016; its own workspace since the repo split began).** A till with `print_mode = 'agent'` does not print on the server: `POST /sales/:id/print` queues one job per copy and answers 202, the agent (on the till PC, connecting OUT) prints and reports, and only then is `sale.print` audited. The server decides duplicate and drawer, never the client or the agent. A print still queued or sent counts as "before" (a second click is a duplicate). The agent has its own token (`X-Agent-Token`, its own one-time code) separate from the till's; `POST /agent/enrol` is the one deliberate extra open door. **A long poll must stop when its client hangs up** (`req.socket` close), or it wakes on the next receipt, claims the job and writes to nobody (a regression test covers it). The agent never prints a job id twice.

- **The till's own server (`till/agent/src/tillServer.ts`, docs/11 §8.4).** It serves `till/web/dist` and passes `/api`, `/uploads` and the live-update stream to the branch server at the address saved in its settings; it decides nothing and imports nothing from another project. **Its own failures carry the header `X-Till-Proxy-Error`** (502 `BRANCH_UNREACHABLE`, 503 `BRANCH_NOT_CONFIGURED`) and `lib/api.ts` turns that into an offline error (status 0): never remove that, or a sale stops going to the queue when the branch server is away; never put it on a real answer of the branch server. It checks `Host` and `Origin` itself (DNS rebinding) and drops `Origin`/`Referer` on the way; its `/till/*` settings routes refuse anyone not on the till PC; a held connection must be released when the screen hangs up (`res.on('close')`). The branch server's address must be in that server's `ALLOWED_HOSTS`. Tests use `http.request` to lie about `Host`/`Origin` because `fetch` will not. The `production-build` browser project runs through it.

- **Run tests from the drive-letter case Windows reports, `C:\`, not `c:\`.** From `c:\...` (what the Bash tool's `cd /c/...` gives) vitest loads its own library twice and every test file dies with `Cannot read properties of undefined (reading 'config')`. Use PowerShell with `Set-Location 'C:\Users\...\POS'`. If tests say `Cannot find package '@pos/shared'`, run `npm install` in that project (the links in its `node_modules/@pos` are missing or point at a folder that was renamed).
- **Database adapter (`db/adapter.ts`, docs/11 §4).** Converted modules (listed in `eslint.config.js`: holds, sales, returns, customers, expenses, services, registers, purchases, inventory, auth/approvals) use `app.database` (`one`, `all`, `run`, `tx`), never `better-sqlite3` or `db/open`. Inside `db.tx()` only `await` database calls: waiting on the event loop (hashing, I/O, a timer) rolls the transaction back with `TX_YIELDED`, so do slow work first. Use `RETURNING id`, `ON CONFLICT`, `?` parameters and `x = x + ?` so the code runs on PostgreSQL later. The legacy `inWriteTransaction` still exists for unconverted modules and refuses (`DB_TX_COLLISION`) to start while another request's adapter transaction is open. Convert a module fully, add its folder to the lint list, keep its tests green.
- **Zod `.partial()` keeps `.default()`.** A PATCH schema built from defaulted fields silently resets those fields on every edit. Keep patch fields free of defaults and put defaults on create only (regression test in `branch-server/tests/integration/products.test.ts`).
- **SQL aliases can shadow columns.** `SUM(l.qty_milli) AS qty_milli` made `HAVING qty_milli` read a single row. Never reuse a real column name as an alias (regression test in `branch-server/tests/db/stock-alerts.test.ts`).
- **Return the row after the update, not before.** Build responses from a fresh read when a write changes what the response shows.
- **supertest:** the test server listens once (`app.listen({ port: 0 })`). Letting supertest start and stop it per request breaks requests built before an `await`.
- **Nothing slow inside a money transaction.** `createSale`, `createReturn`, `receiveCustomerPayment`, `voidSale` and `deleteSale` now run in `db.tx()` (the adapter): transactions never overlap, so two requests cannot interleave and the idempotency check cannot race (`branch-server/tests/integration/concurrent-sales.test.ts`). The body may only `await` database calls; do slow async work (hashing, I/O) before opening the transaction or it is rolled back with `TX_YIELDED`. `catalog`, `users`, `auth` (sign-in and sessions), `settings`, `audit` routes and `reports` still use the legacy synchronous `inWriteTransaction` until they are converted.
- **Idempotency order matters:** the replay check runs inside the transaction, a rejected request is not recorded (so its key can be reused after the fix), and only a successful one stores its answer.
- **Tests that build a table with `it.each` run before `beforeAll`.** Read seeded ids lazily (use thunks).
- **The ETL must never guess silently.** Anything odd in the legacy data is imported as faithfully as the rules allow and added to the report (`branch-server/src/etl/report.ts`). The import refuses to save unless revenue less refunds equals the legacy total. Run it only with the API stopped.
- **The legacy app edited sales on return** (zeroed quantity and total). The new system keeps the original sale and the return apart, so the ETL rebuilds the original. Do not "simplify" this.
- **Shell edits:** the Bash tool halves backslashes. Use Edit/Write for regexes and `\n` or `\u` escapes.
- **A `﻿` escape can come out as a literal invisible byte-order mark** after an edit (seen in the ETL and in `till/tests/e2e/reports.spec.ts`). `npm run lint` catches it (`no-irregular-whitespace`); fix it by character code, not by retyping it.
- **Product pictures: judge the bytes, name by content, serve only our own names.** `storeImage` (`modules/catalog/images.ts`) is the only way a picture enters the pictures folder, from the importer and from the upload alike. Never trust a file extension or a sender's content type (the legacy folder has a ".png" that is WebP and two saved web pages), never accept SVG, and only serve names matching `STORED_NAME`. `Uploads/` is the **old** folder: read it, never write to it (on Windows `Uploads` and `uploads` are the same folder: the importer refuses that). Backups copy the pictures too (`copyMissingPictures`).
- **The Bash tool halves backslashes in Python/JS you pass through it, even in a heredoc**: a `\n` meant for a source file arrives as a real line break (seen again with the importer's and backup tool's messages). Use the Edit tool for any text with a backslash, and check the file after.
- **A reprint is not a sale.** Only the first print of a sale (the one that reaches the printer) is the original and may open the cash drawer; every later print is marked DUPLICATE, never opens the drawer, and is audited (`sale.print`). Do not add a path that prints a receipt without going through that rule, and do not let a client force the drawer open on a reprint. A sale that waits on a till (the outbox) is **not in the system**: it can only leave the outbox by being sent, or by a manager discarding it through `POST /sales/queued-discard`, which leaves a note. Never delete from the outbox without that.
- **A CSV import never guesses and never half-writes.** `importProducts` (`modules/catalog/import.ts`) checks every row first and writes nothing if any row has a problem; `dryRun` defaults to true so a missing flag cannot write; an empty cell leaves a product as it is; units are never created (they decide fractional sales); a barcode shared by several products, or the same barcode or product twice in the file, is an error, not a pick. Excel mangles long barcodes into `7.6E+12`: that is refused, not accepted.
- **The rehearsal must pass on the final dump before cut-over, and it only ever works on a throwaway copy.** `npm run rehearse` (`branch-server/src/cli/rehearse.ts`) imports into a temp folder and deletes it; never point it, or a test, at the real `pos.db`. Its checks must stay independent of one dump's numbers (no hard-coded totals): the cut-over-day dump is a different one. The imported legacy register session is open and must be counted and closed before a new one can be opened (the rehearsal does this step; `docs/10-cutover.md` lists it).
- **Every account needs a way to be created and given a password from the UI**, or cut-over is blocked (a missing Users screen was found by writing the runbook). The admin gives a first password in Menu → Users; with `mustResetPassword` the person is stopped at *Choose your password* before anything else. That stop is in the UI only: the server still accepts the first password. Do not rely on it as a security boundary.
- **A void reverses with new rows and keeps the sale whole.** `voidSale` (`modules/sales/void.ts`) only works while the sale's register session is open (a closed session is immutable and its figures settled: use a return). It puts stock back as `adjustment` movements (`refType: void`), takes each payment out of its register balance and puts the change back, lowers the customer's balance, and sets `status = 'void'` **and `rest_lbp = 0`** (a void sale that still showed money owed would be picked by the next customer payment: a test caught it). The register's rebuilt figures (`computeBreakdown`) and every report already skip void sales; keep it that way for any new report.
- **A stocktake adjusts by what was seen, not by what is there now.** Each count line keeps the system quantity at the moment of counting; finishing posts `counted - that`. Posting `counted - current` would undo every sale made while counting. Only counted products change, and a finished count is frozen by triggers (migration 0008).
- **HTTPS is optional and changes three things together:** `TLS_CERT` + `TLS_KEY` (both or neither), the sign-in cookie becomes `Secure`, and `Strict-Transport-Security` is sent. Anything that reaches the server across a network needs it (`docs/07-operations.md`); localhost does not.
- **The browser-test projects must not share a database when their specs are not repeatable.** `tablet-1024x768` has its own API (3200) and web server (5174). Specs reach the fake printer through the web server's `/__e2e` proxy, never a hard-coded port.
- **A restore from the Backups screen is applied at the next start, never under the running server.** `POST /backups/restore` checks the backup, makes a safety backup, leaves `<db>.restore-pending` and asks the server to stop with exit code 75; the launcher starts it again and `applyPendingRestore` (`backup/pending.ts`) runs before the database is opened. `scripts/dev.mjs` starts the API without the file watcher and restarts it on 75 (a watcher would sit waiting after the exit). Never open the database before that step.
- **Never copy the live database file.** A plain copy can catch a half-written page. Backups use SQLite's online backup (`createBackup`), then switch the copy out of WAL mode so it is one self-contained file (a test caught the companion `-wal`/`-shm` files this otherwise leaves). Restore decrypts and verifies **before** touching anything and keeps the old database (`before-restore-*`).
- **Fastify allows one not-found handler per scope.** `buildApp` sets exactly one (it serves the web app's pages when the built app exists); do not call `setNotFoundHandler` again.
- **Windows PowerShell 5 strips quotes inside arguments passed to programs** (`node -p "a.split(\".\")"` broke the install script's version check). Read `node --version` instead, and keep `.ps1` files ASCII.
- **Reports and sales share one thread unless the report runs in the reports worker** (SQLite is synchronous: a report reading five years of sales held the server for 0.5 s, every till waiting). The two heavy reports (`/reports/sales`, `/reports/products`) run in a worker thread with its own READ-ONLY connection (`modules/reports/runner.ts`, `worker.ts`; the figures are in `compute.ts`, shared by the worker and the inline path). A new report that can read a lot of history belongs there too: add it to `ReportJob` in `compute.ts` and call `app.reports.run(...)`, never a query on `app.db` in the route. The worker inherits `tsx`'s loader flags (so it works under `npm start`); **tests run reports inline** (`startCtx` passes `{ worker: false }`, vitest cannot load TypeScript in a worker) except `reports-worker.test.ts`. Keep report queries on their indexes (`branch-server/tests/db/query-plans.test.ts`) and measure a new one (`docs/09-load-test.md` §6 has the method and the numbers).
- **Migration lists in tests come from the folder**, not a hard-coded array: adding `000N_*.sql` needs no test edit. Keep it that way.
- **Reports attribute by date:** a sale counts on the day it was made and a return on the day it was taken back, and a return is charged to the original sale's cashier. Keep that when adding a report, or the dashboard and the sales report will disagree.

## Conventions

- TypeScript strict. No `any` without a comment.
- Module boundaries in `branch-server/src/modules/*`: call another module through its exported service, never its tables.
- Errors are RFC 7807 with a stable `code` (list in `docs/06-api-spec.md`).
- Tests reference user stories (`US-xx`) in their names. Keep `docs/tests-README.md` traceability current.
- New endpoint → update `docs/06-api-spec.md`, add an integration test, and add it to the RBAC matrix test.
- UI: touch targets ≥ 48 px, every till action keyboard-reachable, RTL-safe CSS (logical properties), Arabic text must render. Use the shared tokens in `styles.css` (no new hex colours or pixel spacings in a page), `components/Icon.tsx` for icons (add a path there; never an emoji or a downloaded icon font; an icon-only button needs an `aria-label`), and add a new page to `lib/nav.ts` (the menu, by role) and, if it is heavy, load it lazily in `App.tsx`. Keep native roles (`link`, `button`) in menus: tests and screen readers rely on them.
- Text on screen goes through `useT()` (`t('English text')`, values as `{name}`); the Arabic is in `lib/ar.ts` and `till/web/tests/i18n.test.ts` fails if one is missing. Use `tNow()` outside a component. Labels kept in lists (the menus) are written in English in the list and translated where they are drawn. Arabic is right to left, so use logical CSS (`start`/`end`, `inset-inline-*`), never `left`/`right`. Receipts and the printer stay English/ASCII whatever the screen language.
- Commit messages: imperative, one concern per commit.

## Legacy data cautions

- `POSDB.sql` is **157 MB**. Never open or `cat` it whole. Use `grep -a`, `sed -n`, `head`. It's T-SQL (`GO` batches, `N'…'` literals, UTF-8 BOM).
- Legacy tables store numbers and dates as strings. `SaleProducts` links to `Sales` only by `reference`. Don't assume FKs exist.
- The dump contains plaintext passwords. Never print them, copy them into docs, or commit them.
- `Uploads/` holds ~700 product images. Treat as read-only input.
